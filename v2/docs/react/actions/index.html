Actions

The server has these routes:

export const routes = {
  getTodos: builder.get(async () => success({ todos })),

  createTodo: builder
    .bodySchema(z.strictObject({ text: z.string().min(1, "Write something first.") }))
    .post(async ({ data }) => {
      if (todos.some((todo) => todo.text === data.body.text)) {
        return zodValidationError([
          { code: "custom", path: ["text"], message: "You already have this todo." },
        ]);
      }
      const todo = { id: todos.length + 1, text: data.body.text, done: false };
      todos.push(todo);
      return success({ todo });
    }),

  toggleTodo: builder
    .paramsSchema(z.strictObject({ id: z.number() }))
    .patch(async ({ data }) => {
      const todo = todos.find((todo) => todo.id === data.params.id)!;
      todo.done = !todo.done;
      return success({ todo });
    }),

  clearCompleted: builder.post(async () => {
    todos = todos.filter((todo) => !todo.done);
    return success({});
  }),
};

useAction​

An action is your own async function. useAction runs it and gives you its state:

function NewTodo() {
  const [text, setText] = useState("");
  const create = useAction(
    async (text: string) => {
      const response = await fetchCuple(client.createTodo.post, {
        body: { text },
      }).thenResolveAlso(["validation-error"]);
      if (response.result === "success") setText("");
      return response;
    },
    { refresh: { success: [client.getTodos] } },
  );

  const issue =
    create.value?.result === "validation-error"
      ? create.value.issues.find((issue) => issue.path[0] === "text")
      : undefined;

  return (
    <form
      onSubmit={(event) => {
        event.preventDefault();
        create.run(text);
      }}
    >
      <input
        value={text}
        onChange={(e) => setText(e.target.value)}
        readOnly={create.isPending}
        aria-busy={create.isPending}
      />
      {issue && <p className="error">{issue.message}</p>}
    </form>
  );
}

In this example:

  • fetchCuple resolves with success and throws anything else. thenResolveAlso(["validation-error"]) lists the one failure this form handles, so it comes back as a typed value instead. Both the schema's error and the custom one are validation-error, with path: ["text"].
  • create.value is what the function returned, typed, so the form can show the issue next to the input.
  • refresh: { success: [...] } names what the action changes, and when: the todos are refetched only when one was created. Nothing else is.

Status​

statusMeaning
idleNothing has happened yet.
pendingRunning, including the refresh it asked for. The screen keeps the old data until the new data lands.
doneYour function finished. value is what it returned, including failures you listed, so check value.result.
failedYour function threw something nobody handled, and errors.onError sent it to "notify" or null. error is the CupleError.

run never rejects. It resolves with the resulting state, so it can go straight into a form library's submit handler.

One action per item​

function TodoItem({ todo }: { todo: Todo }) {
  const toggle = useAction(
    () =>
      fetchCuple(client.toggleTodo.patch, {
        params: { id: todo.id },
      }),
    { refresh: [client.getTodos] },
  );

  return (
    <li className={toggle.isPending ? "pending" : undefined} aria-busy={toggle.isPending}>
      <input
        type="checkbox"
        checked={todo.done}
        onChange={() => toggle.run()}
        disabled={toggle.isPending}
      />{" "}
      {todo.text}
    </li>
  );
}
  • Nothing to handle here but success, so the plain fetchCuple is enough: a failure throws, and goes where unhandled errors go.
  • Call useAction in the item's component, so each todo has its own isPending.
  • aria-busy and the pending class only say what is busy. The stylesheet dims the row and puts a spinner in the button, so the markup stays short and the button keeps its size.

Refresh​

Nothing is refreshed unless the action names it. List what a write changes. When the server computes one thing from another (property cards counting permits), list both:

/** The cache. One per app; plain code (sign-in, SSE handlers) uses it directly. */
export const store = createCupleStore();

/** What each write changes, in one place. Actions name these in `refresh`. */
export const refreshes = {
  notes: [client.getNotes, client.getNote],
  contacts: [client.listContacts, client.getContact],
};

// Switching accounts re-reads only what depends on the account: every call's
// key changed, so each reader reads again under the new one. The previous
// account's data is dropped at once (the default `keepOnKeyChange: false`): the
// next person at this screen may not be the same person.
export function signIn(accountId: AccountId) {
  signedInAs = accountId;
  store.refreshKeys();
}

// Signing out drops everything: nothing of the account stays in memory.
export function signOut() {
  signedInAs = null;
  store.clear();
}
/** One action per row, so each row has its own pending state. */
function NoteRow(props: {
  note: { id: number; text: string };
  onOpen: (id: number) => void;
}) {
  const remove = useAction(
    () =>
      fetchCuple(client.deleteNote.delete, {
        params: { id: props.note.id },
      }),
    // A failed row action shouldn't take the page with it.
    { refresh: refreshes.notes, config: { errors: { onError: "notify" } } },
  );

  return (
    <li className={remove.isPending ? "row pending" : "row"} aria-busy={remove.isPending}>
      <button type="button" className="grow" onClick={() => props.onOpen(props.note.id)}>
        {props.note.text}
      </button>
      <BusyButton
        busy={remove.isPending}
        busyLabel="Deleting"
        onClick={() => remove.run()}
      >
        Delete
      </BusyButton>
    </li>
  );
}
  • Every cached call of a listed endpoint is refetched, and so is every combine that read one of them through get.
  • Only calls something is reading are refetched. The rest are dropped, and fetched fresh when next read. So when you delete the note an open pane shows, and close the pane inside the action, the deleted note is never refetched and never 404s.
  • refresh: [...] refreshes every time the function finishes. refresh: { success: [...] } refreshes only for the listed results, as NewTodo above does; the keys are typed from what the function returns.

Errors​

Errors you handle are results you list with thenResolveAlso, "transport-error" included: typed values in value. Anything else your function throws (a result it didn't list, a network failure it didn't list, a bug) is unhandled, and config.errors.onError decides where it goes: per action, per <Boundary>, or app-wide on the provider:

  • "boundary": the nearest <Boundary>, as a CupleError. The default.
  • "notify": config.errors.notify shows it; the page stays, and the status becomes failed.

Errors never end up only in the console. See Errors for all the cases in one app.

Rules of thumb​

  • When a component moves to another item, give it a key (key={note.id}), or it shows the previous item's result.
  • The state is the latest run's. An earlier run that finishes later still writes and refreshes, but doesn't change what is shown.
  • Steps that must all happen or none belong in one server route. The client can sequence steps, but it can't make them a transaction.
Why it works this way
  • Your own function, not a mutation config. Real writes are sequences: save, then upload, then navigate. Split into mutationFn, onSuccess and onError options, the order things run in becomes something to look up. An async function reads top to bottom.
  • A refresh list, not automatic invalidation. Invalidation by guessed keys either misses something (a stale screen) or refetches everything (a slow one), and neither shows in the code. A list next to the write can be reviewed, and a missing entry shows up as stale data the first time you try it.
  • run never rejects. A rejected promise in an onClick is an unhandled rejection that only reaches the console, and a form library awaiting a rejected submit can leave isSubmitting stuck. Errors go to a boundary or notify instead.
  • The latest run wins. Two quick clicks on a slow network can finish in either order; showing whichever finished last could show the older result.
