# Handling results

`fetchCuple` resolves with `success`. Anything else rejects:

```ts
import { fetchCuple } from "@cuple/client";

const { user } = await fetchCuple(client.getUser.get, { params: { id } });
```

| Outcome | Rejects with |
| ------- | ------------ |
| Any other result: a `404`, an `invalid-body` | `CupleUnexpectedResponseError`, with the `response` |
| No answer: offline, DNS, CORS, a proxy's HTML error page | `CupleTransportError` |
| `signal` aborted | `DOMException` (`AbortError`) |

## Handling a failure: list it

When your code has something to do with a failure, list it. It resolves as a typed value instead of rejecting:

```ts
const res = await fetchCuple(client.createUser.post, { body }).thenResolveAlso([
  "invalid-body",
]);
//    ^? success | invalid-body

if (res.result === "invalid-body") showIssues(res.issues);
```

 - Anything you didn't list still rejects, and goes where unhandled errors go.
 - `"transport-error"` can be listed like any result, for code that has something to do when the server can't be reached (a form that keeps the user's input). It resolves as `{ result: "transport-error", statusCode, message }`. `statusCode` is set when something answered, but not in Cuple's format (a gateway page).
 - `"abort"` can be listed too, for a request you cancel on purpose. It resolves as `{ result: "abort", statusCode: null, message }`.

## Other lists

| Method | Resolves with |
| ------ | ------------- |
| `.thenResolveAlso([...])` | `success`, plus the listed results |
| `.thenResolveOn([...])` | exactly the listed results; `"success"` is not implied |
| `.thenResolveAnyResponse()` | every result the server sent, for code that forwards responses as they are (a proxy, an MCP tool). A network failure or an abort still rejects. |
| `.thenResolveAll()` | everything: every result the server sent, plus `transport-error` and `abort`. Only a bug in your own code rejects. |

```ts
const res = await fetchCuple(client.search.get, { query, options: { signal } }).thenResolveAlso([
  "abort",
]);
if (res.result === "abort") return; // a newer search replaced this one
```

## In React

`@cuple/react` follows the same rule: `useGet` gives you `success`, and `{ resolveAlso: [...] }` lists what the component renders instead. Inside `useAction`, use `thenResolveAlso`. Whatever nobody listed goes to the nearest `<Boundary>`. See [Errors](../react/errors).

:::note[Why it works this way]

The first client, `client.route.get()`, worked like `fetch`: every result resolved, and only a network error threw. Its return type was very complex, and anything built on it had to repeat that type, so `fetchCuple` takes the route as an argument instead.

`fetchCuple` resolves only `success` to match `useGet`. In a component you want the data, and dealing with an error is an enhancement. On its own, resolving everything and unwrapping `success` on request would read slightly better, but one rule across the client and React is worth more.

A failure you list is typed in the return value, with its real shape. A `try/catch` gives you `unknown`. `"transport-error"` and `"abort"` can be listed like any server result, so handling offline or a cancelled request is the same code as handling any other failure.

The lists are chained methods (`.thenResolveAlso([...])`), not an option of `fetchCuple`, because of a typing limit.

:::
