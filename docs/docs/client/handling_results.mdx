# Handling results

`fetchCuple` sends one request and returns a `CuplePromise`: a `Promise` with a few methods that choose which results your code handles.

```ts
import { fetchCuple } from "@cuple/client";

const response = await fetchCuple(client.createUser.post, { body: { email } });
if (response.result === "success") console.log(response.user);
```

By default every answer from the server resolves, whatever its status: a `404` is `{ result: "not-found-error", statusCode: 404, ... }`, typed. Only a missing answer rejects.

| Outcome | | With |
| ------- | - | ---- |
| The server answered in Cuple's format, any status | resolves | the typed result, with `statusCode` |
| No answer: offline, DNS, CORS, a proxy's HTML error page | rejects | `CupleTransportError` |
| `signal` aborted | rejects | `DOMException` (`AbortError`) |

## Only what you handle

Most code handles success and maybe one or two failures. Say which, and the type narrows to them; anything else rejects with `CupleUnexpectedResponseError`:

```ts
// success only
const { user } = await fetchCuple(client.getUser.get, { params: { id } }).thenUnwrap();

// success, or the validation errors a form shows
const res = await fetchCuple(client.createUser.post, { body }).thenResolveAlso(["validation-error"]);
//    ^? success | validation-error

// exactly these results; "success" is not implied
const res = await fetchCuple(client.getUser.get, { params: { id } }).thenResolveOn(["not-found-error"]);
```

## Transport errors as values

`"transport-error"` can be listed like any result. A network failure then resolves instead of rejecting:

```ts
const res = await fetchCuple(client.saveDraft.put, { body }).thenResolveAlso(["transport-error"]);
if (res.result === "transport-error") showOffline(); // { statusCode: number | null, message }
```

`statusCode` is set when something answered but not in Cuple's format (a gateway page); `null` when nothing answered.

## Aborts

```ts
const res = await fetchCuple(client.search.get, { query, signal }).thenWrapAbort();
if (res.result === "abort") return;
```

## In React

`@cuple/react` builds on the same lists: `useGet(..., { resolveAlso })` for reads, `thenResolveAlso` inside `useAction`. Whatever nobody listed goes to the nearest `<Boundary>` with a readable message. See [Errors](../react/errors).

:::note[Why it works this way]

- **API failures are data.** A `404` or a `validation-error` is a normal answer the server chose to send, so it's typed like success and your code can switch on `result`. Only when there's no answer to type does the promise reject.
- **You say what you handle, and the type follows.** Checking every possible result at every call site is noise; listing the few you handle narrows the type to exactly those, and anything else becomes an exception that can't be silently ignored.
- **The HTTP status is never interpreted.** Which `result` goes with which status is the server's decision, so the client never guesses that "4xx means error".
- **One mechanism for every failure you handle.** An offline form is listed the same way as a validation error, instead of needing a `try/catch` next to a result switch.

:::
