# Handling results

`fetchCuple` resolves with `success`. Anything else rejects:

```ts
import { fetchCuple } from "@cuple/client";

const { user } = await fetchCuple(client.getUser.get, { params: { id } });
```

| Outcome | Rejects with |
| ------- | ------------ |
| Any other result: a `404`, a `validation-error` | `CupleUnexpectedResponseError`, with the `response` |
| No answer: offline, DNS, CORS, a proxy's HTML error page | `CupleTransportError` |
| `signal` aborted | `DOMException` (`AbortError`) |

## Handling a failure: list it

When your code has something to do with a failure, list it. It resolves as a typed value instead of rejecting:

```ts
const res = await fetchCuple(client.createUser.post, { body }).thenResolveAlso([
  "validation-error",
]);
//    ^? success | validation-error

if (res.result === "validation-error") showIssues(res.issues);
```

 - Anything you didn't list still rejects, so there's no case you forgot to check.
 - `"transport-error"` can be listed like any result, for code that has something to do when the server can't be reached (a form that keeps the user's input). It resolves as `{ result: "transport-error", statusCode, message }`. `statusCode` is set when something answered, but not in Cuple's format (a gateway page).

## Other lists

| Method | Resolves with |
| ------ | ------------- |
| `.thenResolveAlso([...])` | `success`, plus the listed results |
| `.thenResolveOn([...])` | exactly the listed results; `"success"` is not implied |
| `.thenResolveAll()` | every result the server sent, for code that forwards responses as they are (a proxy, an MCP tool) |
| `.thenWrapAbort()` | adds an abort, as `{ result: "abort" }` |

```ts
const res = await fetchCuple(client.search.get, { query, options: { signal } }).thenWrapAbort();
if (res.result === "abort") return; // a newer search replaced this one
```

## In React

`@cuple/react` follows the same rule: `useGet` gives you `success`, and `{ resolveAlso: [...] }` lists what the component renders instead. Inside `useAction`, use `thenResolveAlso`. Whatever nobody listed goes to the nearest `<Boundary>`. See [Errors](../react/errors).

:::note[Why it works this way]

- **The common case is success.** Most calls have nothing to do with a failure except show it somewhere generic, so checking `result === "success"` at every call site is noise, and forgetting it hands an error to code that expects data.
- **A failure you handle is typed.** Listing it puts it in the return type, so TypeScript checks you handle it, with its real shape (`issues` on a validation error). A `try/catch` gives you `unknown`.
- **One rule everywhere.** `fetchCuple`, `useGet` and `useAction` all start from success and widen by listing, so there's one habit to learn.

:::
