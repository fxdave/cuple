# Configuration

Every behavior is set through one `config` object, grouped by concern. The same shape is accepted in three places:

```tsx
<CupleProvider store={store} config={appConfig}>       // the app's defaults
  <Boundary config={{ cache: { enabled: false } }}>   // everything inside this region
    <Report />                                        // useGet(client.report, args, { config: { ... } })
  </Boundary>
</CupleProvider>
```

Each setting cascades on its own: the request's wins over the Boundary's, over the provider's, over the built-in default. Setting `cache.freshMs` on a Boundary never resets `cache.storeStaleMs` from the provider.

## cache

| Setting | Default | What it does |
| ------- | ------- | ------------ |
| `enabled` | `true` | `false` keeps nothing once it's unread: data is dropped as soon as the last reader unmounts, and fetched again when read again. Readers mounted at the same time still share one request. The same as `freshMs: 0, storeStaleMs: 0`: for search boxes, and large data. |
| `freshMs` | `0` | How long data counts as fresh after it lands. A component that starts reading cached data (another tab, a reopened panel) shows it at once, and refetches it in the background only if it's stale. `0` always refetches, `Infinity` never. Fresh data nobody reads is never dropped. A first load is never fetched twice: "coming back" means some component has read this data before. |
| `storeStaleMs` | 5 minutes | How long data nobody reads stays in memory once it's stale. The clock starts when it is both stale and unread, whichever comes last. With several readers, the longest wins. The calls a combined read makes through `ctx.get` are kept as long as the combined read itself, whatever their own settings. |
| `maxStoredCalls` | `3` | How many calls of one endpoint (or one combined read) nobody reads are kept, whatever `freshMs` and `storeStaleMs` say. Past it, the one unread the longest is dropped. Calls something reads never count, and neither do the calls a cached combined read made. Different args are different calls, so a search keeps its last few queries, not every keystroke. With several readers, the largest wins. |
| `keepOnKeyChange` | `false` | Whether `store.refreshKeys()` keeps data whose key changed: `false` deletes it at once, `true` keeps it like any unread data, so switching back is instant: only when one person owns every account, since the old account's data shows again at once. Read from the provider. |

With `{ freshMs: 30_000, storeStaleMs: 60_000 }`, data that lands at 0s and loses its last reader at 3s is still fresh: it stays, and a reader coming back at 20s gets it without a request. It goes stale at 30s, and is dropped at 90s.

`freshMs` decides only what coming back does: polls, `store.refresh()` and an action's `refresh` refetch fresh data too. With `Infinity`, data nobody reads stays for good: right for reference data, wrong for args that keep changing, like a search, which pile up.

## errors

| Setting | Default | What it does |
| ------- | ------- | ------------ |
| `onError` | `"boundary"` | Actions: where an error nobody handled goes. `"boundary"`, `"notify"`, `null` (handled: the action's `error` holds it, nothing else shows it), or a function choosing per `CupleError`. See [Errors](./errors). |
| `notify` | none | How the app shows an error without replacing the page, given a `CupleError`. Used by `"notify"` and `<Boundary error="notify">`. |
| `fallbackMessage` | `"Something went wrong."` | The `CupleError` message when there's nothing more readable: a network failure, a server result without a message, a bug in production. |

## loading

| Setting | Default | What it does |
| ------- | ------- | ------------ |
| `blocking` | `false` | Counts for `useIsFetching({ blocking: true })`: actions while they run, reads while their data refetches. For a full-page overlay. See [The store](./store#full-page-loading). |
| `everyMs` | none | Reads only: refetch every this many ms while something reads it. |
| `debounceMs` | none | `useGet` only: when its args change, keep showing the current ones until the new ones have stayed the same this long, then load them as a transition, with the current data on screen meanwhile. One request for a burst of typing. The first args load at once. A first load the component moved on from (or unmounted during), and nothing else asked for, is aborted. See [Reading](./reading#when-the-arguments-change). |

## Where each is used

 - `useGet`, `usePages`: `cache`, `loading`.
 - `useAction`: `errors`, `loading.blocking`.
 - `<Boundary error>`: `errors.fallbackMessage`; with `"notify"`, `errors.notify`.
 - Plain code on the store (`store.preload`, `store.refreshKeys`): the provider's config.

:::note[Why it works this way]

- **The same config in three places.** A setting often needs to change for one region (a report that should drop its data when it's closed) or one request. With one shape at every level, moving a setting from a request to a region is a copy-paste, not a different API.
- **Each setting cascades on its own.** A region that only changes `storeStaleMs` shouldn't reset the app's `freshMs`. Merging per setting keeps overrides small.

:::
