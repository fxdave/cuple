# Configuration

Every behavior is set through one `config` object, grouped by concern. The same shape is accepted in three places:

```tsx
<CupleProvider store={store} config={appConfig}>       // the app's defaults
  <Boundary config={{ cache: { keep: 0 } }}>          // everything inside this region
    <Report />                                        // useGet(client.report, args, { config: { ... } })
  </Boundary>
</CupleProvider>
```

Each setting cascades on its own: the request's wins over the Boundary's, over the provider's, over the built-in default. Setting `cache.keep` on a Boundary never resets `cache.refreshOnRead` from the provider.

## cache

| Setting | Default | What it does |
| ------- | ------- | ------------ |
| `keep` | 5 minutes | How long data nobody reads stays in memory. `0` drops it as soon as the last reader unmounts: for large data. With several readers, the longest wins. |
| `refreshOnRead` | `"stale"` | A component starts reading data that's already cached (another tab, a reopened panel): it shows at once, and `"stale"` refetches it in the background if it's older than `freshFor`. `"always"` always does, `"never"` never does. A first load is never fetched twice: "coming back" means some component has read this data before. |
| `freshFor` | `0` | How long data counts as fresh for `"stale"`, in ms. |
| `onKeyChange` | `"drop"` | What `store.refreshKeys()` does with data whose key changed: `"drop"` deletes it at once, `"keep"` keeps it for `keep`, so switching back is instant: only when one person owns every account, since the old account's data shows again at once. Read from the provider. |

## errors

| Setting | Default | What it does |
| ------- | ------- | ------------ |
| `unhandled` | `"boundary"` | Actions: where an error nobody handled goes. `"boundary"`, `"notify"`, or a function choosing per `CupleError`. See [Errors](./errors). |
| `notify` | none | How the app shows an error without replacing the page, given a `CupleError`. Used by `"notify"` and `<Boundary error="notify">`. |
| `message` | `"Something went wrong."` | The `CupleError` message when there's nothing more readable: a network failure, a server result without a message, a bug in production. |

## loading

| Setting | Default | What it does |
| ------- | ------- | ------------ |
| `blocking` | `false` | Counts for `useIsFetching({ blocking: true })`: actions while they run, reads while their data refetches. For a full-page overlay. See [The store](./store#full-page-loading). |
| `every` | none | Reads only: refetch every this many ms while something reads it. |

## Where each is used

 - `useGet`, `usePages`: `cache`, `loading`.
 - `useAction`: `errors`, `loading.blocking`.
 - `<Boundary error>`: `errors.message`; with `"notify"`, `errors.notify`.
 - Plain code on the store (`store.preload`, `store.refreshKeys`): the provider's config.

:::note[Why it works this way]

- **One object, one shape everywhere.** You learn the settings once; the provider, a `<Boundary>` and a single request all take the same `config`, so moving a setting from one request to a whole region is a copy-paste.
- **Grouped by concern.** `cache`, `errors` and `loading` are what you tune, and they're easy to find by name in the editor instead of a flat list of flags.
- **Each setting cascades on its own.** A region that only changes `keep` shouldn't silently reset the app's `refreshOnRead`. Merging per setting keeps overrides small and local.
- **Layout-shaped defaults.** `<Boundary>` already marks a region of the UI; attaching config there follows how people think about screens ("this report panel") rather than individual endpoints.

:::
