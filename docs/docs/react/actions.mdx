## useAction

An action is your own async function. `useAction` runs it and gives you its state:

```tsx file=../../../examples/docs/todos/app.tsx#new-todo
```

In this example:

 - `fetchCuple` resolves with `success` and throws anything else. `thenResolveAlso(["invalid-body"])` lists the one failure this form handles, so it comes back as a typed value instead. Both the schema's error and the custom one are `invalid-body`, with `path: ["text"]`.
 - `create.value` is what the function returned, typed, so the form can show the issue next to the input.
 - `refresh: { success: [...] }` names what the action changes, and when: the todos are refetched only when one was created. Nothing else is.

### Status

| `status`  | Meaning |
| --------- | ------- |
| `idle`    | Nothing has happened yet. |
| `pending` | Running, including the refresh it asked for. The screen keeps the old data until the new data lands. |
| `done`    | Your function finished. `value` is what it returned, including failures you listed, so check `value.result`. |
| `failed`  | Your function threw something nobody handled, and `errors.onError` sent it to `"notify"` or `null`. `error` is the `CupleError`. |

`run` never rejects. It resolves with the resulting state, so it can go straight into a form library's submit handler.

## Refresh

Nothing is refreshed unless the action names it. List what a write changes. When the server computes one thing from another (property cards counting permits), list both:

```ts file=../../../examples/react/src/client.ts#store
```

```tsx file=../../../examples/react/src/App.tsx#note-row
```

 - Every cached call of a listed endpoint is refetched, and so is every `combine` that read one of them through `get`.
 - Only calls something is reading are refetched. The rest are dropped, and fetched fresh when next read. So when you delete the note an open pane shows, and close the pane inside the action, the deleted note is never refetched and never 404s.
 - `refresh: [...]` refreshes every time the function finishes. `refresh: { success: [...] }` refreshes only for the listed results, as `NewTodo` above does; the keys are typed from what the function returns.

## Errors

Errors you handle are results you list with `thenResolveAlso`, `"transport-error"` included: typed values in `value`. Anything else your function throws (a result it didn't list, a network failure it didn't list, a bug) is unhandled, and `config.errors.onError` decides where it goes: per action, per `<Boundary>`, or app-wide on the provider:

- `"boundary"`: the nearest `<Boundary>`, as a `CupleError`. The default.
- `"notify"`: `config.errors.notify` shows it; the page stays, and the status becomes `failed`.

Errors never end up only in the console. See [Errors](./errors) for all the cases in one app.

## Rules of thumb

 - When a component moves to another item, give it a `key` (`key={note.id}`), or it shows the previous item's result.
 - The state is the latest run's. An earlier run that finishes later still writes and refreshes, but doesn't change what is shown.
 - Steps that must all happen or none belong in one server route. The client can sequence steps, but it can't make them a transaction.
